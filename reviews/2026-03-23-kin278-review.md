## Finding #1 — Critical — `conftest.py` dependency overrides return plain dicts instead of Pydantic models

**File:** `tests/conftest.py`

```python
REGULAR_USER = {
    "id": REGULAR_USER_ID,
    "email": "user@example.com",
    "name": "Test User",
    "role": "user",
    "disabled_at": None,
}

app.dependency_overrides[get_current_user] = lambda: REGULAR_USER
```

`get_current_user` is typed to return `CurrentUser` (a Pydantic `BaseModel`). Route handlers throughout the codebase use attribute access: `current_user.id`, `current_user.role`, `current_user.email`. On a plain Python dict, these raise `AttributeError` — `{"id": "..."}["id"]` works, but `{"id": "..."}.id` does not.

Every test that hits any route will fail with `AttributeError: 'dict' object has no attribute 'id'` before any assertion runs.

**Fix:** Import `UserContext` (or `CurrentUser`) and return Pydantic model instances:

```python
from app.auth import UserContext

REGULAR_USER = UserContext(
    id=REGULAR_USER_ID,
    email="user@example.com",
    name="Test User",
    role="user",
    disabled_at=None,
)

ADMIN_USER = UserContext(
    id=ADMIN_USER_ID,
    email="admin@example.com",
    name="Test Admin",
    role="admin",
    disabled_at=None,
)

OTHER_USER = UserContext(
    id=OTHER_USER_ID,
    email="other@example.com",
    name="Other User",
    role="user",
    disabled_at=None,
)
```

No other changes needed — `require_admin` depends on `get_current_user` so the override cascades correctly once the return type is fixed.

## Non-blocking notes

**`TestDefaultModel.test_set_valid_generation_model`** — The test asserts `resp.json()["default_model_id"] == "gpt-4o"`, but `default_model_id` on the `users` table is a UUID FK to `llm_models`, not the `model_id` string. The assertion should check for the UUID returned by the add-model call, not the string `"gpt-4o"`. This will be a false pass if the endpoint returns the UUID row ID and `"gpt-4o" != UUID`.

**`REGULAR_USER_ID` / `OTHER_USER_ID` imported in `test_admin_users.py`** but these UUIDs are used directly as path params. If the test DB doesn't have rows for these UUIDs in the `users` table (since there's no DB seeding in conftest), admin endpoints that do `SELECT * FROM users WHERE id = OTHER_USER_ID` will 404. The test DB setup will need seeded user rows or the admin routes need to handle unknown-but-valid UUIDs gracefully.
