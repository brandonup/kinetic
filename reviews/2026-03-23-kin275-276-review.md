### Finding #1 — Critical — Token budget formula wrong

**File:** `context_stack.py:_enforce_budget()`

```python
budget = int(context_window * 0.80)  # current
```

ADR-003 §5 specifies:
```
budget = model_context_window - RESPONSE_BUFFER_TOKENS
where RESPONSE_BUFFER_TOKENS = 2048
```

For a 128k model: `0.80 × 128000 = 102,400` vs `128000 - 2048 = 125,952`. The implementation is reserving 20% (25,600 tokens) as buffer instead of the specified 2,048. This over-truncates context for large models, degrading response quality unnecessarily.

**Fix:** Replace with `budget = context_window - 2048` (expose `RESPONSE_BUFFER_TOKENS = 2048` as a module constant).

### Finding #2 — Important — Layer truncation caps wrong for L3 and L1

**File:** `context_stack.py:_enforce_budget()`

ADR-003 §5.2 soft caps:

| Layer | ADR-003 cap | Current code |
|---|---|---|
| L1 | 500 tokens | 200 tokens (`200 * 4 = 800 chars`) |
| L2 | 300 tokens | 300 tokens ✅ |
| L3 | 2,000 tokens | 500 tokens (`500 * 4 = 2000 chars`) |

L3 (project instructions) is capped at 500 tokens instead of 2,000. This is a 4× reduction that will heavily truncate project instructions.
L1 (user bio) is capped at 200 instead of 500.

**Fix:**
```python
_truncate_layer(stack, "l3_project_instructions", 2000 * 4)  # was 500 * 4
_truncate_layer(stack, "l2_company",              300  * 4)  # correct
_truncate_layer(stack, "l1_user_bio",             500  * 4)  # was 200 * 4
```

### Finding #3 — Critical — Conversation summary dropped from LLM messages

**File:** `conversations.py:_build_llm_messages()`

`_fetch_history()` returns the compression summary as a `role: "system"` message:
```python
history: list[dict] = [
    {"role": "system", "content": f"[Summary of earlier conversation]\n{summary['summary_text']}"},
    ...verbatim messages...
]
```

`_build_llm_messages()` filters history to only `user` and `assistant`:
```python
for msg in context.history:
    if msg["role"] in ("user", "assistant"):  # ← "system" dropped
        messages.append(...)
```

The summary is silently discarded. Compressed conversations lose all context older than the verbatim window.

**Fix:** Include `"system"` in the allowed roles, or handle the summary separately as a prefixed system block:
```python
for msg in context.history:
    if msg["role"] in ("user", "assistant", "system"):
        messages.append({"role": msg["role"], "content": msg["content"]})
```

### Finding #4 — Critical — `done: true` sent before persistence

**File:** `conversations.py:event_stream()`

Same root cause as KIN-300. `yield done: true` is inside the `try` block for LLM streaming errors, immediately after the `async for delta` loop — before the persistence code runs:

```python
try:
    async for delta in stream_completion(...):
        full_response += delta
        yield delta event

    yield done: true   # ← BEFORE persistence

except ...: ...

# Persistence happens here — too late
try:
    await _run(persist...)
except Exception:
    yield error event
    return
```

Client receives `done: true` before the assistant message exists in the DB. On page reload, the message is gone.

**Fix:** Move `yield done: true` to after the persistence block. See KIN-300 review for the corrected structure.

### Finding #5 — Minor — Missing `[DONE]` SSE stream sentinel

**File:** `conversations.py:event_stream()`

The stream never sends `data: [DONE]\n\n`. Some SSE clients and proxy layers (including the Next.js proxy) use this sentinel to detect stream completion reliably, separate from the `done: true` JSON event.

The Next.js SSE proxy route (`app/api/stream/route.ts`) may depend on this. Confirm whether the frontend handles stream termination from connection close alone, or expects `[DONE]`. If the proxy waits for `[DONE]`, the client will hang until the connection times out.

**Fix:** Add after `yield done: true`:
```python
yield "data: [DONE]\n\n"
```
