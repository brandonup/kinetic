## Gap #2 — Blocking — BYOK "first available" fallback is undefined

**Spec §Dependencies:**
> "The system selects a generation model matching the user's configured keys (default model preferred, else first available)."

"First available" is not deterministic. Which provider is tried first if the user has both OpenAI and Anthropic keys? The implementation needs a defined order to avoid non-deterministic behavior across deploys.

**Action required:** Define the fallback order explicitly. Recommended: use provider list order from `llm_models` table ordered by `created_at ASC` (first admin-added model wins). Alternatively, hard-code a provider preference order (e.g., anthropic → openai → google → groq).

## Gap #3 — Blocking — Server-side BYOK gate not specified

The spec says the frontend hides the upload button when no API keys are configured. KIN-312 asks to confirm the "server-side mirror." The spec's API endpoint section does not document this:

| Endpoint | What happens with no API key? |
|---|---|
| `POST /api/profile/upload-document` | ❓ not specified |
| `POST /api/company/{id}/upload-document` | ❓ not specified |
| `POST /api/agent/{id}/upload-document` | ❓ not specified |

The server must enforce this independently — frontend gates are bypassed by direct API calls. The spec must state: **"Return 400 with `error: byok_key_required` if the user has no API keys configured."**

**Action required:** Add the 400 response to the API endpoint section of the spec.

## Gap #4 — Blocking — File storage during extraction is ambiguous

**Spec §Dependencies:**
> "File storage for temporary processing (Supabase Storage, auto-deleted post-extraction)"

The Overview says the file is "discarded once fields are populated." If the implementation uses Supabase Storage for temp files, any extraction failure (LLM error, timeout, parsing exception) leaves an orphaned file in storage. Supabase Storage doesn't auto-delete files on a timer without explicit TTL configuration (which is not standard in Supabase).

If the spec intent is in-memory processing, the "Supabase Storage" mention is misleading and should be removed. In-memory is the correct approach: receive the multipart file bytes, extract text (pdf/docx parsing), call LLM, return extracted fields, discard bytes. No storage writes.

**Action required:** Clarify whether extraction is in-memory or uses Supabase Storage. If in-memory (recommended): remove the "Supabase Storage" sentence. If Supabase Storage: specify the TTL/cleanup mechanism.

## Non-blocking notes

**Prompt versioning:** The spec defines 6 prompts inline. Per conventions, prompts must be in a prompts module with ID and version, not hardcoded in the route handler. The implementation ticket (KIN-310/KIN-311) should reference a specific prompts module path (e.g., `app/prompts/linked_upload.py`). Flag this in the implementation ticket.

**Agent instructions token target:** The `generate-agent-instructions` prompt specifies "300–500 tokens." The implementation should enforce this via `max_tokens=600` in the LLM call (with headroom), then truncate the output at 500 tokens if needed. This is not specified in the spec but is needed to prevent runaway instruction generation.
